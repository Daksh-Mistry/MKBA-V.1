# Configuration and deployment

[Documentation index](README.md) | [Beginner setup](GETTING_STARTED.md) | [Development](DEVELOPMENT.md)

## Normal setup needs no configuration edits

Use `START_ROBO.cmd` on the computer and `bash start_robo.sh` for the Pi API. Start video separately with `bash start_camera.sh` in another Pi terminal. The computer creates consistent private service settings and discovers the Pi. The only optional normal-user entry is `CHAT_API_KEY` in the root `.env` for broader conversation. Leave it blank for local chat.

Settings below are for debugging or deliberate architecture changes. They are not extra prerequisites for running Robo.

`PI_CAMERA_ENABLED` is retained only for compatibility with older configuration. Neither Pi launcher uses it to enable video. Start or stop `start_camera.sh` explicitly; it needs no Python environment. The API and camera use separate locks in `PI/bin/` and have independent lifetimes.

## Where settings live

| File/location | Owner and role |
|---|---|
| Root `.env` | Optional `CHAT_API_KEY`, read by `run_stack.py`. Standalone `python -m ML` does not read this root key file. |
| `Backend/.env` | Pi/ML URLs, backend listener, internal service tokens, model selection and hardware/policy switches. |
| `ML/.env` | Listener/token, registered camera/model settings, inference options and chat provider/model. |
| `Frontend/.env` | Listener, private Backend address/token, local sign-in and advanced browser origins. |
| `PI/.env` | Optional Pi overrides only. Normal Bookworm launch requires no such file and no Pi token. |
| `PI/config.py` | Hardware pin/channel constants and Pi protocol defaults; changes need corresponding physical and API tests. |
| `ML/models/registry.json` | Allowed model IDs, runtime, local artifact paths, labels and identity. This is not an API-key file. |
| `PI/mediamtx.yml` | Camera source and RTSP/WebRTC transport configuration. |

Full per-service variable/default/constraint tables belong to the [Backend](../Backend/README.md), [Frontend](../Frontend/README.md), [ML](../ML/README.md) and [Pi](../PI/README.md) guides. Keep a new setting in its owning service's reference and `.env.example`; do not scatter duplicate tables with different defaults.

## Automatic startup versus standalone startup

`startup.prepare_settings()` intentionally repairs **generated** settings on every normal start:

- Generates missing/invalid computer service tokens and makes each shared token match its two services.
- Keeps `ROBO_UI_TOKEN` different from the Backend bearer token.
- Restores local-only listeners and `FRONTEND_LOCAL_ACCESS=true`.
- Repairs malformed service ports and aligns the Frontend→Backend and Backend→ML URLs.
- Aligns `ML_STREAM_ID` between ML and Backend, preferring ML's configured nonempty ID.
- Enables Backend's speech forwarding capability; the UI still speaks only on request.
- Creates the optional root key file if absent. Existing provider/model choices are preserved.

The runtime supervisor then chooses unused computer ports and maps those URLs into its children. A discovered Pi replaces control, WHEP, viewer and RTSP host settings **for that run**. The camera path/ports generated by `use_pi` are currently fixed to `cam`, 8554 and 8889.

Therefore, changing a service listener to a remote host or a custom camera URL in `.env` is not enough if the normal supervisor later normalizes it. For custom topology, run the services individually or deliberately change the supervisor mapping. Do not fight automatic configuration with repeated file edits.

`configure.py` is an advanced utility. It rejects conflicting existing service tokens instead of repairing them, and `--pi-host` accepts a hostname/IPv4 address, not a URL, path or port. Some console hints still mention the previous manual startup; the supported automatic path is the launcher.

## Environment precedence

For the normal computer stack:

1. Automatic preparation writes/repairs the component files.
2. `run_stack.environment()` loads ML, Backend and Frontend settings and checks shared values.
3. Existing process environment values override file values.
4. A **nonempty root `CHAT_API_KEY`** overrides the component-file key unless the process environment explicitly defines `CHAT_API_KEY` (even as blank).
5. Runtime port selection, Pi discovery and simulation apply their own run-specific mappings.
6. `service_environment()` filters keys for each child. Only ML receives chat credentials; Frontend never receives the cloud key or ML bearer token.

For standalone services, each service loads its own `.env` and honors process environment overrides. Check its README before copying a launch command into another directory. A blank root key does not erase an existing nonempty key in `ML/.env`; clear the actual configured source if intentionally returning to keyless mode.

The simple configuration writer supports ordinary `NAME=value` strings; it does not run shell expressions or interpolate variables. Do not paste PowerShell/Bash code into an `.env` expecting it to execute.

## Typical changes

| Goal | Change and verification |
|---|---|
| Add the default LLM key | Root `.env` `CHAT_API_KEY`, restart normal stack, inspect the actual reply mode. Health configuration is not proof that a provider request succeeded. |
| Change provider/model | `ML/.env` `CHAT_BASE_URL`, `CHAT_MODEL`, key and token-limit field; restart. Base URL stops at `/v1`, not `/chat/completions`. See [ML](../ML/README.md). |
| Replace fire weights | Add a distinct registry entry/artifact, verify hash/labels and adapter compatibility, select the registered model while stopped. See [ML replacement recipe](../ML/README.md). |
| Set an explicit known Pi | `configure.py --pi-host YOUR_PI_HOST` from the prepared environment; normal discovery probes it first. This is optional, especially useful with multiple robots or blocked multicast. |
| Use a different Pi API port | Pi override plus matching preferred URL or mDNS advertisement; HTTP and WS ports must agree. Discovery advertises the Pi's actual API port. |
| Move ML to another computer | Advanced standalone Backend `ROBO_ML_URL`, matching ML token, reachable ML listener and direct Pi RTSP access. Normal supervisor assumes local ML. |
| Serve UI on another device | Advanced standalone Frontend bind/origins and token login; set `FRONTEND_LOCAL_ACCESS=false`. The viewer device must also reach Pi video. |
| Change GPIO/servo/IR convention | Pi hardware/config plus Backend `robot_profile`/sensor/aiming assumptions; perform simulation and controlled physical checks. A software default cannot calibrate wiring. |
| Tune auto thresholds | `Backend/config.py` settings and `auto_policy.py` as appropriate. The current HTTP auto-config endpoint is read-only; not every dataclass field is an environment variable. |

## Credentials and network roles

| Value | Shared between | Normal user entry? |
|---|---|---|
| `ROBO_SERVICE_TOKEN` | Frontend and Backend | No, generated. |
| `ML_SERVICE_TOKEN` | Backend and ML | No, generated. |
| `ROBO_UI_TOKEN` | Frontend's advanced token login | No for loopback automatic sign-in. |
| `CHAT_API_KEY` | ML and optional chat provider | Optional. |
| Pi token | None in Pi API 2.3 | No. |

Do not mix these tokens or paste private `.env` files into reports. Local sign-in requires an exact same-origin request on a loopback-bound frontend. LAN mode must use its advanced authentication/origin configuration. The existing Pi API has no authentication; direct clients on its reachable network can take its single controller connection. The Backend's checks do not protect a direct Pi connection that bypasses it.

## Generated files and backups

| Path | Contents and handling |
|---|---|
| `.runtime/` | Private runtime downloads, managed Python installation/cache, dependency signature, library caches, install/stack locks and current stack URL. Reusable; not source. |
| `.venv/` | Computer Python environment; tied to its platform/base interpreter. Rebuild rather than copying between machines. |
| `ML/models/weights/` | Verified local model artifacts. Keep revision/hash information with a custom artifact. |
| `logs/` | Appended computer service logs. No built-in log rotation; retain only what your deployment needs. |
| `PI/.venv`, `PI/bin/` | Pi environment and camera binary; `bin/setup.log` contains the latest setup output, `bin/discovery.log` contains discovery output, and API/camera have separate launcher locks. Created locally on Pi. |
| `dist/pi-ready.tar.gz` | Generated source bundle, ignored by Git. Rebuild after Pi or documentation changes. |
| Component/root `.env` | Private configuration. Back up separately with appropriate access controls. |

OS-held locks release after a crashed process exits. Do not delete a lock file to bypass a still-running installer/controller. When moving the checkout, recreate environments if their interpreter paths no longer resolve; the normal use case is installation in its final directory.

## Updating a deployment

1. Stop robot actions and the affected launchers.
2. Keep a known-good source revision, private settings and custom model registry/artifacts for rollback. Do not restore an old in-memory action/session.
3. Update the computer source. Run `START_ROBO.cmd -Check`; dependency changes are detected by the recipe/signature.
4. Rebuild `dist/pi-ready.tar.gz` with `scripts/package_pi.py`, copy/extract it over the chosen Pi source directory, then run the Pi API and independent camera launchers. The bundle preserves excluded settings/environments; the API launcher performs setup checks and the camera launcher verifies its own streamer.
5. Start the computer stack and verify service identity, model availability, keyless chat and read-only telemetry before resuming hardware actions.

The current `.service` file under Pi is an optional systemd **template** with user/path placeholders from an older deployment. It is not installed by copying the repository. Follow the Pi guide if deliberately adopting systemd and choose one supervisor; do not launch duplicate controllers.
